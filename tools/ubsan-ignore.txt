# UBSan ignorelist -- excludes the UAE 68k core from UndefinedBehaviorSanitizer.
#
# The UAE core contains 8 known UB sites (negative shift exponents, left shifts
# overflowing int, left shift of a negative value). They are analysed and
# recorded in ROADMAP.md and are deliberately NOT fixed: the standing rule is
# "don't touch the UAE core". They are value-benign on two's-complement
# hardware, so they indicate no wrong emulation result today.
#
# Without this file UBSan is useless as a gate. The very first instruction
# dispatched trips newcpu.c:229, so with -fno-sanitize-recover every single test
# aborts, and WITHOUT that flag UBSan only writes to stderr -- which the Swift
# harness reads and discards. Either way, real UB in os9exec's own code is
# invisible. Excluding the core makes a UBSan failure mean something.
#
# Usage:
#   make -B CC="cc -fsanitize=address,undefined -fno-sanitize-recover=undefined \
#             -fsanitize-ignorelist=tools/ubsan-ignore.txt -g"
#   swift run --package-path test
#
# CLANG ONLY. GCC has no -fsanitize-ignorelist and rejects the flag outright, so
# a GCC UBSan build cannot use this and will abort on the UAE core instead. GCC
# ASan alone is fine and needs no ignorelist -- the UAE findings are all UBSan
# ones -- which is how the big-endian sanitizer run is done.
#
# If the UAE UB is ever addressed (ROADMAP has the upstream-friendly fix), drop
# this file rather than letting it hide new problems.
#
# The section header is what keeps this to UBSan. An entry outside any section
# applies to EVERY sanitizer, so the same list passed to an ASan build (the
# sweeps and the fuzzers do) switched ASan off for the whole UAE core too:
# newcpu.o had no ASan checks at all. [undefined] is the UBSan group, and
# alignment is part of it.
