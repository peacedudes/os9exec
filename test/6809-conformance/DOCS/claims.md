# Conformance claims

Every test in this suite asserts one documented Microware behaviour. This
table records, for each test, the document and section the expectation
comes from -- not a description we wrote ourselves, and not our own
curated error-code notes. Facts only; no manual text is copied verbatim.

| Test | Citation | Expected behaviour |
|------|----------|---------------------|
| t01  | OS-9 System Programmers Manual (6809): Chapter 11 introduction (before 11.1), page 73; section 11.3.11 (I$Open); Appendix B.1, error-code table entry for E$PNNF. Microware Training and Education, "OS-9 System Overview" course text, pages 44-45, Table 5. | I$Open's own error list (11.3.11) does not include E$PNNF, but the manual's Chapter 11 introduction explains that an error not in a call's own list was probably returned by another system call the main call made -- here, the file-manager lookup I$Open dispatches to. The Appendix B.1 table independently defines E$PNNF as the code for a pathlist that cannot be located, and the training text states, as the baseline case it compares pipe-opening behaviour against, that opening a file that does not exist returns that same error. Together they establish that `I$Open` of a pathlist with no corresponding file reports E$PNNF (216), not silent success and not a different error code. |
| t02  | BASIC09 Programming Language Reference Manual, Revision G (Microware Systems Corp.), Chapter 7 "Data Types, Variables and Data Structures", page 7-2, "Type INTEGER" section (`os9/txtResources/6809/BASIC09_Reference_Manual_Rev_G.txt`, verified directly against the manual text, not the skill's summary of it). | The manual states that a BASIC09 `INTEGER` on the 6809 target occupies two bytes and holds a signed value from -32768 through 32767. It then states directly that arithmetic producing a result outside that range does not cause a run-time error -- the result cycles back into range modulo 65536, giving the worked example 32767 + 1 yields -32768. This establishes that `INTEGER` is a 16-bit signed type on 6809 and that overflow is silent, defined wraparound, not a trapped error and not clamping. |
| t03  | OS-9 System Programmers Manual (6809): section 11.3.12 (I$Read), page 108; Appendix B.1, error-code table entry for E$EOF, page 133 (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text). | The I$Read FUNCTION text states plainly that once all data in a file has been read, the next I$Read service request returns an end-of-file error -- this is stated directly in prose, not left to inference the way t01's E$PNNF was. The call's own POSSIBLE ERRORS list (E$BPNum, E$BMode) does not separately name it, the same pattern already established for t01: an error a call's prose describes but its summary list omits still applies. The Appendix B.1 table independently defines that code as E$EOF (211), "end of file encountered on read." Together they establish that `I$Read` against a file whose data has already been fully consumed reports E$EOF (211), not a zero-byte success and not a different code. |
