# Conformance claims

Every test in this suite asserts one documented Microware behaviour. This
table records, for each test, the document and section the expectation
comes from -- not a description we wrote ourselves, and not our own
curated error-code notes. Facts only; no manual text is copied verbatim.

| Test | Citation | Expected behaviour |
|------|----------|---------------------|
| t01  | OS-9 System Programmers Manual (6809): Chapter 11 introduction (before 11.1), page 73; section 11.3.11 (I$Open); Appendix B.1, error-code table entry for E$PNNF. Microware Training and Education, "OS-9 System Overview" course text, pages 44-45, Table 5. | I$Open's own error list (11.3.11) does not include E$PNNF, but the manual's Chapter 11 introduction explains that an error not in a call's own list was probably returned by another system call the main call made -- here, the file-manager lookup I$Open dispatches to. The Appendix B.1 table independently defines E$PNNF as the code for a pathlist that cannot be located, and the training text states, as the baseline case it compares pipe-opening behaviour against, that opening a file that does not exist returns that same error. Together they establish that `I$Open` of a pathlist with no corresponding file reports E$PNNF (216), not silent success and not a different error code. |
| t02  | BASIC09 Programming Language Reference Manual, Revision G (Microware Systems Corp.), Chapter 7 "Data Types, Variables and Data Structures", page 7-2, "Type INTEGER" section (`os9/txtResources/6809/BASIC09_Reference_Manual_Rev_G.txt`, verified directly against the manual text, not the skill's summary of it). | The manual states that a BASIC09 `INTEGER` on the 6809 target occupies two bytes and holds a signed value from -32768 through 32767. It then states directly that arithmetic producing a result outside that range does not cause a run-time error -- the result cycles back into range modulo 65536, giving the worked example 32767 + 1 yields -32768. This establishes that `INTEGER` is a 16-bit signed type on 6809 and that overflow is silent, defined wraparound, not a trapped error and not clamping. |
| t03  | OS-9 System Programmers Manual (6809): section 11.3.12 (I$Read), page 108; Appendix B.1, error-code table entry for E$EOF, page 133 (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text). | I$Read's FUNCTION paragraph promises exactly one outcome once a file's content has already been fully consumed: the following read attempt fails rather than silently returning zero bytes -- stated directly in prose, not left to inference the way t01's E$PNNF was. The call's own POSSIBLE ERRORS list (E$BPNum, E$BMode) omits it, the same gap already documented for t01: an error a call's prose describes but its summary list omits still applies. Appendix B.1 supplies the actual code: 211, assigned to the read-time end-of-file condition. Combined, the two passages establish that `I$Read` issued against an exhausted file reports E$EOF (211), never a zero-byte success and never a different code. |
| t04  | OS-9 System Programmers Manual (6809): section 11.3.16 (I$Write), page 114; section 11.3.11 (I$Open), page 107; Appendix B.1, error-code table entry for E$BMode, page 133 (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text). | I$Write's FUNCTION text requires the path to have been OPENed or CREATEd in WRITE or UPDATE mode, and its own POSSIBLE ERRORS list names E$BMode outright (unlike t03's E$EOF, no inference needed here). I$Open's own section defines access mode 1 as read-only. Appendix B.1 independently assigns E$BMode code 203, covering an I/O request a device or file's current mode cannot honor. Together they establish that `I$Write` against a path opened in mode 1 (read) reports E$BMode (203), not silent success and not a different code. |
| t05  | OS-9 System Programmers Manual (6809): section 11.3.11 (I$Open), page 107; section 11.1.9 (F$ID), page 80; Appendix B.1, error-code table entry for E$FNA, page 132 (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text). OS-9 Operating System User's Manual (Gimix, 1983 printing, Copyright 1981 Microware Systems Corporation): Command Descriptions, LOGIN, page 7-32, password-file field 3 (`os9/txtResources/6809/Gimix_OS-9_Users_Manual_1983.txt`, verified directly against the manual text). | I$Open's FUNCTION text states that the requested access mode must conform to the file's access-permission attributes, and that only the owner may access a file unless the file's public-permit bits allow it. Appendix B.1 assigns E$FNA (214) to that failure. F$ID's FUNCTION text defines the value it returns in Y as a single flat integer from 0 to 65535, not a split group/user pair, and the LOGIN password-file field description independently states that this same identity's value 0, and only 0, is the superuser. Together, opening a file without adequate permission reports E$FNA (214), and the one identity this manual exempts from that check is the flat user ID 0. Checked directly against this suite's own guest before shipping: NitrOS-9's `/DD/SYS/password` on the disk this suite boots holds flat, ungrouped ID numbers exactly as the manual describes (`0` for the boot account, `1`-`4` for the login accounts), not a 68k-style group.user pair -- so t05fna's guard tests F$ID's whole 16-bit Y value against zero, matching the manual's own single-identity rule with no divergence to disclose here. (An OS-9/68000-derived assumption that 6809 also packs group.user was tried first and rejected live: it treated every account on this guest as a superuser, because every ID here is under 256, so testing only Y's high byte SKIPped even an ordinary logged-in user.) The test also assumes its operator is neither `SCRATCH/denied`'s owner (the build account) nor user ID 0; only the ID-0 half is machine-checked. |
| t06  | OS-9 System Programmers Manual (6809): section 11.3.14 (I$Seek), page 109 (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text; independently cross-checked against the OS-9 Level One System Programmer's Manual Rev F1 1983 edition, same page content). | I$Seek's INPUT fields state plainly that X holds the most-significant 16 bits and U the least-significant 16 bits of the 32-bit desired file position -- an X:U split, spelled out in the register description itself, no inference needed. This matches `test/6809-live-verification/syscall-iseek.a`'s already-live-verified finding on this suite's NitrOS-9 guest exactly: manual and live system agree. (The 68k `I$Seek` carries its position in D1 instead -- a real architecture difference, but not one this manual's own 6809 text has any discrepancy with; an earlier hedge in the live-verification test's own header comment, written before that manual passage was pinned down, is superseded by this citation.) |
| t07  | BASIC09 Programming Language Reference Manual, Revision G (Microware Systems Corp.): Appendix C - Error Codes, page C-1, entry for code 45; Program Statements and Structure chapter, ON ERROR GOTO Statement section, page 9-10 (`os9/txtResources/6809/BASIC09_Reference_Manual_Rev_G.txt`, verified directly against the manual text). | Appendix C's own numbered table assigns code 45 to a divide-by-zero condition, one entry in the same 10-through-80 range the appendix itself marks as BASIC09's own language-level codes, distinct from the codes OS-9 or an external program returns. The ON ERROR GOTO section shows the companion ERR function is how a trapped procedure retrieves that numeric code, resetting to zero once read. On 6809, BASIC09 has no hardware divide instruction, so it must check the divisor itself before dividing, landing squarely in that language-level table; INTEGER division by a zero divisor therefore reports 45, not a code from OS-9's own separate error space. (This same manual's language is shared with 68k BASIC09, but a divide-by-zero there reaches a real 68000 hardware trap first, landing in the OS-9-level number space instead -- a genuine target difference, not one this citation disputes for 6809; this correction is discussed in the task report.) |
| t08  | OS-9 System Programmers Manual (6809): section 11.3.14 (I$Seek), page 109; section 11.3.16 (I$Write), page 114 (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text). BASIC09 Programming Language Reference Manual, Revision G (Microware Systems Corp.): Input and Output Statements chapter, CREATE Statement section, page 10-5 (`os9/txtResources/6809/BASIC09_Reference_Manual_Rev_G.txt`, verified directly against the manual text). | I$Seek's own FUNCTION paragraph states plainly that a seek may target any position at all, even one beyond the file's current size, and that a subsequent write is what actually grows the file to reach it -- a read at such a position still reports end-of-file; seeking alone never allocates anything. I$Write's own FUNCTION paragraph states the same growth from the write side: data written past the file's present end automatically expands it. BASIC09's own CREATE Statement section restates this at the language level for its own PRINT/WRITE/PUT statements. Together they establish that seeking a path past its current end and then writing there leaves the file exactly as long as that seek position plus the bytes written, neither truncated back to the old length nor left sized at the seek position alone. |
| t09  | OS-9 System Programmers Manual (6809): section 6.6 (RBF Record Locking) introduction, page 46; section 6.6.1, "Record Locking and Unlocking", page 46; section 6.6.5, "Specific Details for Particular I/O Functions", Read/ReadLine and Write/WriteLine paragraphs, pages 47-48 (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text). | Section 6.6's own introduction states the purpose plainly: to preserve the integrity of a file more than one process can reach, RBF detects when a process reads a record another process is in the middle of modifying and defers that read until the record is safe again. Section 6.6.1 then gives the update cycle as an explicit worked sequence -- the read locks the record, the rewriting write releases it -- and states that on a path opened in update mode any read at all locks what it read, because RBF cannot know in advance whether the caller intends to rewrite it; the lock stands until that path's next read, write or close. Section 6.6.5's Write paragraph restates the release from the writing side. Together these establish that two processes each doing an unprotected read-modify-write cycle on the same record of one file are serialized by the mechanism itself, with no locking call anywhere in either program, so neither can overwrite the other's update -- the classic lost update cannot occur. |
| t10  | OS-9 System Programmers Manual (6809): section 6.6.3, "End of File Lock", page 47; section 6.6.5, Read/ReadLine and Write/WriteLine paragraphs, pages 47-48 (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text). | Section 6.6.3 states that a process reading or writing at the end of a file thereby gains EOF Lock, and keeps the end locked until it performs a read or write that is not at the end. It states in the same paragraph that this is the only circumstance in which a write call automatically locks any part of a file, and gives the reason: to avoid the trouble that arises when two processes try to extend one file at the same time. Its closing illustration is a spooler reading a listing file an assembler is still writing, and states that record locking keeps the reader one step behind the writer. Section 6.6.5 supplies the release rule, that a lock is dropped by the path's next read, write or close. Together they establish that a reader which catches up to a live producer waits at the current end instead of taking the current end for the final one and reading short. |
| t11  | OS-9 System Programmers Manual (6809): section 6.6.3, "End of File Lock", page 47, sequential-output paragraph; section 6.6.1, page 46, for the scope of the update-mode restriction (`os9/txtResources/6809/OS-9_System_Programmers_Manual.txt`, verified directly against the manual text). Independently corroborated in three further Microware-derived manuals carrying the same passage: OS-9 Technical Reference (Tandy), line 3799; OS-9 Level Two Development System (Tandy), line 12732; OS-9/68000 v2.4 Technical Reference Manual, line 6307. | Section 6.6.3 states that a program creating a file for sequential output gains EOF Lock as soon as the file is created, and that no other process is then able to pass that writer through the file. The manual's own illustration of this is an assembly listing redirected to a disk file -- ordinary redirected output, which is a write-only path, not an update one -- with a spooler reading it. The mode restriction stated in section 6.6.1 is scoped to reads: it says reading a path opened in read or execute mode does not lock, because those modes cannot update a record. Nothing in either section conditions the EOF lock on update mode, and section 6.6.3 states outright that a write at the end of file is the one case where a write locks. Together they establish that a write-only producer holds the EOF lock exactly as an update-mode one does, and a reader following it waits at the edge the same way. (This is the reverse of what this project's own notes previously asserted, which is why it is tested: the claim that a write-only path takes no lock cannot be pinned to any manual, and contradicts the spooler design the manual describes.) |
