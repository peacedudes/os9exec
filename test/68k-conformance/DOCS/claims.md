# Conformance claims — CONF68K

Every test in this suite asserts one documented Microware behaviour. This
table records, for each test, the document and page the expectation comes
from — not a description we wrote ourselves, and not this project's own
curated error-code notes. Facts only; no manual text is copied verbatim.

Unless stated otherwise the source is the **OS-9/68000 Operating System
Technical Manual, version 2.4** (Microware Systems Corporation), read
directly as `os9/txtResources/68k/OS-9_v2.4_Technical_Reference_Manual.txt`
rather than from any summary of it. Its Chapter 1 covers user-state system
calls (`F$…`, paginated `1 - n`), Chapter 2 the I/O system calls (`I$…`,
paginated `2 - n`), and its error-code appendix is paginated
`Error Codes - n`.

A note on what these citations do and do not settle. The manual is the
specification; a running system — including os9exec, and including
NitrOS-9 — is a candidate implementation of it. Where the two disagree the
manual wins and the system has a defect to explain. That is the whole
premise of the suite: a FAIL is a disagreement with the citation in this
table, not with our emulator's behaviour.

| Test | Citation | Expected behaviour |
|------|----------|---------------------|
| t01 | I$Open, POSSIBLE ERRORS, page 2 - 17; error-code appendix entry for E$PNNF, page Error Codes - 5. | I$Open's own error list names E$PNNF, and the appendix defines that code, 216, as the one reported when the specified pathlist cannot be found. No inference is needed: unlike the 6809 manual — where the same claim has to be assembled from the chapter introduction plus the error table, as the 6809 suite's t01 records — the 68k manual lists the error against the call itself. So opening a pathlist with no corresponding file reports 216, neither silent success nor some other code. |
| t02 | I$Read, FUNCTION and POSSIBLE ERRORS, page 2 - 18; error-code appendix entry for E$EOF, page Error Codes - 5. | I$Read's FUNCTION text states that once all data in a file has been read, the next I$Read request returns an end-of-file error, and E$EOF appears in the call's own error list. The appendix assigns 211 to an end-of-file condition met on a read. So a read issued against a file whose content is already exhausted reports 211 — not a zero-byte success. |
| t03 | I$Write, FUNCTION and POSSIBLE ERRORS, page 2 - 30; I$Open access-mode bits, page 2 - 16; error-code appendix entry for E$BMode, page Error Codes - 4. | I$Write's FUNCTION text requires the path to have been opened or created in write or update mode, and names E$BMode in its own error list. I$Open's mode-bit table defines bit 0 as read access, so mode 1 grants read and nothing else. The appendix assigns 203 to an I/O function the file or device is incapable of. Together: writing to a path opened with mode 1 reports 203. |
| t04 | I$Open, FUNCTION text including its NOTE on an all-zero access mode, page 2 - 16. | The manual states directly that a non-directory file may be opened with no mode bits set at all, and gives the purpose: the caller can then examine the file's attributes and size through I$GetStt. It states in the same passage that such a path permits no actual I/O. The first half of that is this test: the open itself must succeed rather than being rejected as a malformed request. |
| t05 | I$Open, FUNCTION text and its all-zero-access-mode NOTE, page 2 - 16; error-code appendix entry for E$BMode, page Error Codes - 4. | The second half of the same passage: a path opened with no mode bits permits no actual I/O, and the appendix defines 203 as the code for an I/O function the file or device cannot perform. So a read on such a path must be refused, and refused with 203. Taken with t04 this pins both ends — a system that rejects the open is wrong, and so is one that allows the read. Worth having as a pair because mode 0 arises by accident as well as by design: POSIX `O_RDONLY` is 0, while OS-9 read access is bit 0 set, so C code ported without adjustment asks for no access at all and looks to the programmer like it asked for read. |
| t06 | I$Read, FUNCTION text, page 2 - 18. | The same FUNCTION paragraph that establishes t02 also states the converse for a read that cannot be fully satisfied: fewer bytes are read than were requested, and this is explicitly not an end-of-file error. So a 64-byte read of a 4-byte file succeeds and reports 4 bytes read. This is the half a test written only around "did the read fail" would miss, which is why it is separate from t02. |
| t07 | I$Seek, INPUT register description and FUNCTION text, page 2 - 20; I$Write, FUNCTION text, page 2 - 30; I$GetStt SS_Size, page 2 - 13. | I$Seek's FUNCTION text states a seek may be made to any position even when the file is not that large, and that subsequent writes automatically expand the file to the required size. I$Write's own text states the same from the writing side: data written past the present end of file expands it. I$GetStt's SS_Size function returns the current file size in d2.l. So seeking to 70000, writing 5 bytes, and asking for the size must give exactly 70005. I$Seek's INPUT description gives the position as d1.l, a full 32-bit byte offset, which is why the seek target is deliberately above 65535: a target inside 16 bits would pass equally well on a system honouring only the low half. |
| t08 | I$Seek, FUNCTION text, page 2 - 20; error-code appendix entry for E$EOF, page Error Codes - 5. | The same I$Seek passage that permits seeking past the end states that reads there return an end-of-file condition, and that a seek by itself does not initiate anything on the media. So a read at position 1000 of a 4-byte file reports 211, and the file is not extended by the attempt. With t07 this establishes the division of labour the manual describes: the seek commits to nothing, the write is what grows the file. |
| t09 | Error-code appendix entry for E$BPNum, page Error Codes - 4; I$Read, POSSIBLE ERRORS, page 2 - 18. | The appendix defines 201 as a path number that was too large or refers to a path that does not exist, and says it can arise whenever a path number is passed to an I/O call. I$Read lists E$BPNum among its own possible errors. So an I$Read quoting a path number that is not open reports 201. |
| t10 | I$Create, FUNCTION text, page 2 - 5; error-code appendix entry for E$CEF, page Error Codes - 5. | I$Create's FUNCTION text states that an error occurs if the pathlist specifies a file name that already exists, and the appendix assigns 218 to an attempt to create a file under a name already present in the directory. So a second create of the same name reports 218 rather than reopening or truncating the existing file. (This is the test that found a real divergence on its first run — see `ourruns.md`.) |
| t11 | I$Seek, FUNCTION text including its NOTE, page 2 - 20. | I$Seek's FUNCTION text states outright that a seek to address zero is the same as a rewind. So after a file has been read to its end, seeking to 0 and reading again returns the file's first byte. The observed value here is that byte rather than an error code, because the failure this test exists to catch — a seek that reports success and leaves the file pointer where it was — produces no error at all. |
| t12 | I$Write, FUNCTION text, page 2 - 30; I$GetStt SS_Size, page 2 - 13. | I$Write's FUNCTION text states that data written past the present end of file automatically expands the file, and SS_Size returns the current size. So six successive 50-byte writes to a new file must leave it reporting 300 bytes. Several writes rather than one deliberately: a system tracking only the largest single write, or only the most recent one, cannot be told apart from a correct one by a single-write test. |
| t13 | F$Event: Ev$Read, INPUT/OUTPUT and FUNCTION text, page 1 - 23; Ev$Creat, page 1 - 20; Ev$Wait, page 1 - 22. | Ev$Read's FUNCTION text says it "reads the value of an event without waiting or modifying the event variable", and its OUTPUT gives that value in d1.l. Ev$Creat establishes that the wait auto-increment is applied "each time the event ... is waited for", and Ev$Wait is the call that applies it. So on an event created with a non-zero wait increment, two successive Ev$Read calls must both report the created value. Both choices matter: with a zero increment a system that wrongly applied it would be indistinguishable from one that did not, and with only one read, "returned the value from before its own increment" also looks correct. |
| t14 | F$Event: Ev$Signl, INPUT and FUNCTION text, page 1 - 26; Ev$Creat, page 1 - 20. | Ev$Signl's INPUT is given as "d1.w = MS bit set to activate all processes in range / LS bits = 8". The MS bit is therefore a modifier sharing the word with the function code, not a distinct call, and d1 = $8008 is the documented spelling of a broadcast signal. Its FUNCTION text says the event variable is updated with the signal auto-increment specified at creation. So signalling that way on an event created with an increment of 5 must move a value of 100 to 105. A single-process test cannot observe the waking half of the flag; what it pins down is that setting the bit does not stop the call being recognised as a signal. |
| t15 | F$Event: Ev$Set, INPUT/OUTPUT and FUNCTION text, page 1 - 27. | Ev$Set takes "d2.l = new event value" and returns "d1.l = previous event value" — the value held before the call, not the one just installed, which is what makes it usable as an atomic read-and-replace. The two values are far apart and neither is zero, so a system returning the new value, or nothing, cannot coincide with the right answer. |
| t16 | F$Event: Ev$SetR, INPUT/OUTPUT and FUNCTION text, page 1 - 27; Ev$Signl, page 1 - 26. | Ev$SetR is "similar to Ev$Signl, but instead of using the signal auto-increment value to update the event variable, the value in d2 is used", with d2 documented as a signed increment. So the event moves BY d2 — not by the signal auto-increment as Ev$Signl would, and not TO d2 as Ev$Set would. The event is created with a signal auto-increment different from the increment passed, and the increment differs from the result, so all three confusions land on different numbers. |
| t17 | F$Event: Ev$Info, INPUT/OUTPUT and FUNCTION text, page 1 - 24; F$Event FUNCTION, event field list, page 1 - 18. | Ev$Info "returns a copy of the 32-byte event table entry", indexed by "the system event number" taken from the low word of d0, and returns the index it found in d0. The F$Event overview lists the entry's fields in order — ID, name, value, wait increment, signal increment, link count, next, previous — and states a name of at most 12 characters, a four-byte value, and two queue pointers; in a 32-byte entry that leaves exactly one word each for the remaining four fields, putting the value at offset 14. The search loops rather than assuming index 0: a real system may hold events of its own in lower slots, and pinning the index would report somebody else's event as a divergence. |
| t18 | F$Event: Ev$WaitR, INPUT/OUTPUT and FUNCTION text, page 1 - 23. | For Ev$WaitR "the range specified in d2 and d3 is relative to the current event value. The event value is added to d2 and d3 respectively, and the actual values are returned to the caller." So a relative minimum of 0 against an event holding 100 must come back as 100. The range is chosen so that NEITHER reading blocks — relative [0,+500] resolves to [100,600], which contains 100, and taken wrongly as absolute [0,500] it contains 100 as well — because a test that hung on the wrong answer would report nothing instead of reporting a divergence. |

| t19 | I$Open access modes, page 2 - 16; Record Locking and Unlocking, page 7 - 8; Record Locking Details for I/O Functions (Read/ReadLine), page 7 - 11; I$SetStt SS_Ticks; error-code appendix entry for E$Lock. | "When a file is opened in update mode, ANY read causes the record to be locked out because RBF does not know in advance if the record will be updated", and the locked area "includes all bytes starting with the current file pointer and extending for the number of bytes requested". E$Lock, 252, is "RECORD IS LOCKED-OUT - Another process is accessing the requested record". SS_Ticks with a delay interval of one means "if the record is not released immediately, an error is returned". So a second process writing into a range the first has read, on a path opened for update, is told 252 rather than made to wait. This is the first test in the suite needing two processes: RBF exempts a process from its own locks ("RBF notices that the same process owns both paths and keeps them from locking each other out"), so no single-process test can reach this claim at all. |
| t20 | Record Locking and Unlocking, page 7 - 8; Record Locking Details for I/O Functions (Read/ReadLine), page 7 - 11; Open/Create guidance, page 7 - 10. | "Reading files that are opened in read or execute modes does not cause record locking to occur because records cannot be updated in these two modes", restated for the calls themselves: "Read and ReadLine cause lock out of records only if the file is open in update mode." So another process may write bytes this one has just read. This is t19 with one bit of the access mode changed, and it is the half a suite built only around "does a lock happen" would omit — a system that locks on every read passes t19 and fails here, producing exactly what the manual warns of: "if shared files are routinely opened for update on a multi-user system, users can become hopelessly record-locked for extended periods of time." It is also the control for this suite's own two-process machinery, since it shares t19's rescue schedule and comes back promptly. |
| t21 | Record Locking, page 7 - 7; Record Locking Details for I/O Functions, page 7 - 11; I$SetStt SS_Ticks. | Record locking exists to recognise "when a process is trying to read a record that another process may be modifying" and to defer "the read request until the record is safe" — the reading side is the case the mechanism was designed around. With SS_Ticks at 1 the deferred reader is told 252 instead of waiting. This is t19 with the CONTENDING operation changed from a write to a read, and it is here to localise rather than to broaden: an implementation that handles the two paths differently reports two different observations across the pair and is caught in the act, which no single test using only one of them could do. |
| t22 | Record Locking and Unlocking, page 7 - 8; Record Locking Details for I/O Functions (Write/WriteLine), page 7 - 11. | "The record remains locked until the next read, write, or close occurs", and from the writing side, "Write calls always release any record that is locked out." The documented update sequence is read / update / reposition / rewrite, at which point "RECORD IS RELEASED". So after the holder rewrites what it read, another process may write those bytes. Without this, t19 would be satisfied by a system that locks on first read and never lets go — every conflict test would still pass and the file would be unusable. The rewrite is at position zero of a hundred-byte file, deliberately not at the end, because a write AT the end gains EOF lock instead of releasing it (t25/t26). |
| t23 | I$SetStt SS_Lock, INPUT and FUNCTION text. | "If $FFFFFFFF bytes are requested, then the entire file is locked out regardless of where the file pointer is. This is a special type of file lock that remains in effect until released by SS_Lock(0), a read or write of zero bytes, or the file is closed." The same entry notes "There is no way to gain file lock using only read or write system calls", so this call is the only route to the behaviour. The holder seeks to 90 and the contender writes at 0: that gap is the test, since an implementation measuring the range from the current position would leave byte 0 free and be indistinguishable from a correct one if both processes worked near the same offset. |
| t24 | I$SetStt SS_Lock, FUNCTION text. | "If 0 bytes are requested, all locks are removed (Record Lock, EOF Lock, and File Lock)", and the file-lock passage names SS_Lock(0) first among the things that end it. This is t23 plus the release, and it is what stops t23 being satisfiable by a system that simply never lets anything through. The pair must be read together: t23 alone says a lock can be taken, t24 alone says a write can succeed, and only together do they say the lock is a lock rather than a permanent refusal. They differ by exactly one call. |
| t25 | End of File Lock, page 7 - 9; Record Locking Details for I/O Functions (Write/WriteLine), page 7 - 11. | "An EOF lock occurs when the user reads or writes data at the end of file. The user keeps the end of file locked until a read or write is performed that is not at the end of the file. EOF lock is the only time that a write call automatically causes lock out of any part of the file. This avoids problems that could occur when two users try to simultaneously extend a file." Two things make this unlike every other lock here: it is taken by WRITING, and nothing asked for it — the manual is explicit that this is the sole such case. The stated purpose names the case under test, so a second process writing at the end must be refused. The holder never closes the file, because creating it and writing to its end is the whole of taking this lock: "As soon as the file is created, EOF lock is gained, and no other process is able to pass the writer in processing the file." |
| t26 | Record Locking Details for I/O Functions (Read/ReadLine and Write/WriteLine), page 7 - 11. | "Any read or write of zero bytes releases any record lock, EOF lock, or File lock", and the Write entry repeats it: "a write of zero bytes releases EOF lock and File lock." This is the release half of t25 and the only documented way to put down an EOF lock without giving up position or closing the file — the ordinary rule, "until a read or write is performed that is not at the end of the file", cannot apply to a process that means to stay at the end. A zero-length write is otherwise a no-op, which is precisely why an implementation is likely to optimise it away and lose the release with it. |
| t27 | I$Open, access-mode bit table and FUNCTION text, page 2 - 16; Non-sharable Files, page 7 - 8; error-code appendix entry for E$Share. | I$Open's mode table gives bit 6 as "open file for non sharable use", and "If the single user bit is set, the file is opened for non-sharable access even if the file is sharable." Page 7-8 gives what the second process sees: "If the single-user bit is set, only one process may open the file at a time. If another process attempts to open the file, error (#253) is returned." The holder sets the bit in the ACCESS MODE rather than in the file's attributes, the form the manual recommends for the common case ("a file needs to be non-sharable only during the execution of a specific program"), which also leaves nothing on the disk to clean up. Alone among the conflict tests the contended operation is an OPEN, and an open that must be refused cannot be an open that waits — so this one reports a real verdict even on a system where a blocked reader or writer would never be resumed. |
| t28 | Record Locking Details for I/O Functions (Read/ReadLine), page 7 - 11. | "The locked out area includes all bytes starting with the current file pointer and extending for the number of bytes requested." So a fifty-byte read at position zero locks [0,50) and leaves the rest alone: another process may write at 60 with no conflict. This is the upper bound on t19's claim, and the pair is what makes either one mean anything — t19 alone is satisfied by a system that locks the whole file, or the whole device, on any read, which would be catastrophic on a shared file and would still pass. The contending write is past the locked range and short of end of file, so neither the record lock nor EOF lock can account for a refusal. |
| t29 | Record Locking and Unlocking, the NOTE on multiple paths, page 7 - 8. | "Only one portion of a file may be locked out at one time. If an application requires more than one record to be locked out, multiple paths to the same file may be opened with each path having its own record locked out. RBF notices that the same process owns both paths and keeps them from locking each other out." So a read through one path and a write through another, from the SAME process, must not conflict. This exemption is what every other test in this group depends on being real — it is why none of them can be written as a single process. It is checked rather than assumed because a system that lost it would not fail loudly: it would deadlock a program against itself, which looks like the program hanging. Both paths are opened by the forked child even though the claim needs no second process, purely so the parent can rescue it; a process that locks itself out has nobody to release it. |
| t30 | Error-code appendix entry for E$Share, page Error Codes - 5; I$Delete, page 2 - 8. | The appendix entry for 253 ends "A common way to get this error is to attempt to delete a file that is currently open", and I$Delete requires the caller to have non-sharable write access to the file. So deleting a file another process holds open reports 253. Like t27 the contended operation cannot block — a delete that must be refused is not a delete that waits — so this reports a real verdict even where a blocked reader or writer is never resumed. Unlike t27 the holder asks for nothing unusual, just an ordinary update-mode open, which makes this the case a program is most likely to meet by accident. |
| t31 | Record Locking Details for I/O Functions (Read/ReadLine), page 7 - 11. | "Any read or write of zero bytes releases any record lock, EOF lock, or File lock." t26 checks the write half against EOF lock; this is the read half against a record lock, and they are separate calls down separate paths in any implementation. The sentence immediately before it is what makes this worth having separately: "Releasing a record does not normally release EOF lock." Zero-length access is therefore not a synonym for the ordinary release but a stronger operation, and a system could implement the ordinary rules correctly and still not honour this one. |
| t32 | I$SetStt SS_Ticks, page 2 - 24; error-code appendix entry for E$UnkSvc, page Error Codes - 4. | SS_Ticks is an RBF SetStat. A file manager that does not implement a given SetStat must report E$UnkSvc — the appendix defines 208 as an unknown service request — rather than doing something undefined. `/nil` is not an RBF device on any medium, so the claim reads the same on a host directory and on an image, which is why this test does not SKIP like the locking group. It runs LAST deliberately: the defect it was written for was a call through an uninitialised dispatch slot, and from the end of the run a regression costs only this test's own line instead of turning every later test into a MISSING. |
| t33 | F$Fork / F$Wait, pages 1-30 and 1-71; I$Write, page 2 - 30. | An access that no other path has locked succeeds immediately. It is the negative control for the two-process group: every other test there concludes "the lock held" from a NON-zero observation, so all of them would still report exactly that if the fork/rescue harness could never return 0 — a contend that always timed out, a child that always died, a marker protocol that always looked blocked. This test is the other half, and it was verified by sabotage: making `chsaw` always report BLOCKED turns it from obs=0 into obs=901 while every locking test still passes. The parent deliberately holds nothing (it closes the path it created the file on, which is what drops the EOF lock, then reopens read-only and never reads), so the answer does not depend on the device having record locking — which makes this the only two-process test that runs rather than SKIPs on a host-native directory, and therefore the only one CI exercises. |
| t34 | F$Julian, page 1 - 40, FUNCTION and CAVEATS. | "To compute the number of days between two dates, subtract the lower Julian date number from the higher number." The calendar is Gregorian -- the same page fixes the reform at October 15, 1582 -- so the difference across February 2000 is 29: 2000 is divisible by 400 and is a leap year. This is deliberately a DIFFERENCE rather than a conversion. The corpus test it was promoted from (test/68k-live-verification/batch9-01.a) converts a date and converts it back, and its own header admits what that cannot show: a round trip reproduces its input bit-for-bit whatever epoch or calendar the implementation uses, so it pins the register contract and nothing else. A difference has a value the manual fixes independently of the epoch, so the system can disagree with it. Paired with t35, which is the case that actually catches a wrong rule. |
| t35 | F$Julian, page 1 - 40, FUNCTION and CAVEATS. | The same subtraction rule across February 1900, which has 28 days: 1900 is divisible by 100 but not by 400, so the Gregorian calendar the manual's reform date commits it to makes it an ordinary year. This is the discriminating half of the pair. An implementation using the plain every-four-years rule passes t34 and fails here, reporting 29; one with no leap-year handling at all fails both. Neither is reachable by the round trip these were promoted from. |
| t36 | F$CRC, page 1 - 25, FUNCTION and CAVEATS; module header M$Size, page 1 - 8. | "An easier method of checking an existing module's CRC is to perform the calculation on the entire module, including the module CRC. The CRC accumulator contains the CRC constant bytes if the module CRC is correct... Its value is $00800FE3", with "The CRC accumulator must be initialized to $FFFFFFFF before the first F$CRC call". The module under test is the test itself: F$Link returns its header in a2, M$Size is "the overall module size in bytes, including header and CRC", and a module OS-9 agreed to load necessarily has a correct CRC -- so no particular data is needed, which matters because the manual fixes no CRC for any given byte string, only this constant for a whole correct module. **The comparison is over 24 bits, not 32.** The same CAVEATS paragraph says the CRC "is three bytes long, in a four-byte field" and that "F$CRC always returns $FF in the most significant byte of d1", so the accumulator is $FF800FE3 and CRCCon's leading $00 is a 24-bit value printed in a 32-bit field. A first cut of this test compared the full high word, observed $FF80, and would have recorded a FAIL against a system doing exactly what the manual says. This test takes the middle byte, $80. |
| t37 | F$CRC, page 1 - 25, as t36. | The low word of the same constant, $0FE3. Split from t36 because $800FE3 is 8392675 and the report's field is six digits, where the suite prints OVRFLW rather than a plausible-looking truncation -- so the constant is checked as two observations that are each genuinely observed, rather than one that is not. Together they pin all 24 bits. |
| t38 | F$CmpNam, page 1 - 22. | "?" matches any single character and "*" matches any string, so pattern `*?` must match target `ab` -- `*` takes `a`, `?` takes `b`. **This found a real defect** (fixed): after a `*` the matcher scanned the target for the next pattern character compared LITERALLY, so a `?` following a `*` was hunted for as an actual `?` byte and never found. A 60,000-case fuzz against ordinary glob semantics produced 2296 disagreements, every one a false negative. F$CmpNam is the primitive behind shell wildcard expansion, so the symptom is files silently missing from a wildcard. Promoted from test/68k-live-verification/batch1-01.a, which called F$CmpNam only with patterns the old code happened to get right. |
| t39 | F$CmpNam, page 1 - 22. | The same call on a pattern built to make a backtracking matcher explode, `***?a*??*`. There is no manual claim about cost, so what is asserted is the ordinary one -- that it returns the right answer -- and the test's value is that it must RETURN AT ALL. A matcher that recurses per `*` takes exponential time on this shape; the implementation keeps one remembered `*` and one resume point, so its cost is bounded by pattern x target. A regression to a recursive matcher shows up here as a test that never reports, which the suite counts as MISSING rather than as a pass. |
| t40 | F$Event Ev$Pulse, page 1 - 25. | "The event variable is set to the value passed in d2, and the signal auto-increment is not applied. Then, the Ev$Signl search routine is executed and the original event value is restored." Single process, so the event queue is empty and the search finds nobody -- which is exactly what isolates the last clause: with nothing to wake, a pulse must have no observable effect whatsoever. The three constants are far apart so that every wrong answer is a different number. 999 means the pulsed value was left behind, so the search ran and the restore did not; 105 means the signal auto-increment was applied and the call was therefore treated as an Ev$Signl; 208 means it was refused outright, which is what os9exec answered until the event queue was built. The wait auto-increment is 0 deliberately: the search applies it as it wakes each process, so it cannot fire with nobody queued, but the manual does not settle what a pulse would leave behind if it did, and a test should not need that question answered to be trusted. |
| t41 | F$Event Ev$Pulse, page 1 - 25; Ev$Wait, page 1 - 22. | The half t40 cannot reach: that a pulse is seen at all. Its whole observable effect is on processes ALREADY in the event queue, because the value it sets is restored before the call returns -- so no single process can catch one however quickly it looks, and two are the minimum. The child links the event by name, announces itself, and blocks on the range [7,7] against an event holding 0; the parent pulses 7, and the child reports what Ev$Wait handed back ("d1.l = actual event value"). A pulse that woke nobody yields no number at all: the child stays blocked, the parent's timeout expires, and it is killed and reported as 902. **Verified by sabotage** -- removing the search from the pulse turns this test from obs=7 into obs=902 while t40 still passes, so the two are measuring different things. This is the claim the two-process harness could not reach until now; see the note on ordering below. |
| t42 | F$Event Ev$Signl, page 1 - 26; Ev$Wait, page 1 - 22. | Ev$Signl "signals that an event has occurred. The current event variable is updated with the signal auto-increment specified when the event was created. Then, the event queue is searched for the first process waiting for that event value", and a waiter suspended out of range waits until "an Ev$Signl occurs that puts the value in range". t14 checks the arithmetic half of that sentence and is single-process, so it has nobody waiting: a system can update the variable correctly and never wake anyone. This is the wake, and it is the ORDINARY case where t41's pulse is the exotic one -- the shape a program actually uses. It is kept deliberately parallel to t41, same event, same handshake, same range, so the pair differs in exactly one thing: the call the parent makes. What it reports is what the PARENT reads once the child has woken, because that is the one observation that separates the two calls -- a signal leaves its value behind, a pulse restores the old one, and the child cannot tell the difference since both wake it with the same number. |

## Claims deliberately not tested here

Recorded so that their absence reads as a decision rather than an oversight.

- **Permission enforcement (E$FNA, 214).** Needs an operator who is neither
  the file's owner nor a member of group 0, so the test can only report SKIP
  when run by the account that built the disk. The 6809 suite's t05 does
  exactly this and is instructive about the cost: most of its citation is
  taken up explaining which identity model applies.
- **F$ID's group/user packing.** The manual (page 1 - 38) gives d1.l as the
  process's group and user number, both word values. That is a genuine 68k
  fact worth having in the suite, but a machine-checkable assertion needs a
  known expected identity, and the suite cannot know which account a
  recipient runs it under.

## What the two-process tests assume

t19 through t31 need a second process, and so do t41 and t42. Arranging one costs assumptions that the single-process tests above do not make. They are recorded here rather than left to be discovered from an intermittent result.

- **The holder acts before it forks.** Every lock these tests are about is taken before F$Fork is called, so no handshake is needed to establish it: a child cannot have started before the call that created it. This is why the locking tests are reproducible. **t41 and t42 invert it, and could not be written until the ordering problem was faced**: a wake is observable only to a process already waiting, so there the CHILD must be blocked before the PARENT acts. Nothing reports "I am asleep now", so it uses the same readiness marker with the same residual race as everything else here -- and the parent's own timeout is what turns a pulse that arrived too early into an honest 902 rather than a hung run.
- **The parent rescues the child rather than trusting SS_Ticks.** A test that hangs reports nothing and takes the rest of the run with it, so the holder releases everything on a timer and, if the child still has not finished, kills it. That is what makes 902 -- "never came back" -- an observable outcome instead of a dead run.
- **The readiness handshake marks intent, not blocking.** The child creates SCRATCH/ready immediately before its contended call, because nothing a process can do observes its own impending sleep. If it were descheduled in that gap for the whole of the release delay, it would report BLOCKED (901) on a system that would have answered E$Lock. The delay is set far above the few instructions in the gap, but the possibility is real and is the one source of flakiness these tests have.
- **The locking tests need a device with real record locking.** On anything else they report SKIP, carrying the code the device gave. That is why DOCS/expected and DOCS/expected-rbf are separate files: the same test is a verdict on an image and a SKIP on a host-native directory, and one file could only record one of them. t41 and t42 are not in that group: F$Event is a kernel call with no file manager underneath it, so they report the same verdict on both.
